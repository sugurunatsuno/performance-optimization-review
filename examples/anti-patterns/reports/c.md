# C アンチパターン最適化レポート

対象: `examples/anti-patterns/c/{baseline.c,optimized.c}`
環境: AMD Ryzen 5 7430U (6C/12T), 15GiB, Linux, gcc 16.2.1, `-O3 -fopenmp` (baseline/optimized で同一)
負荷: 実行中 load average ≈ 2.3（他プロセスあり）。数値はすべて `RESULT` 行の 3 レップ中央値。

## 1. 実行したコマンド

```bash
cd examples/anti-patterns/c
python3 ./scripts/detect_profilers.py .
python3 ./scripts/find_candidates.py .
gcc -O3 -fopenmp -o baseline baseline.c
gcc -O3 -fopenmp -o optimized optimized.c
for i in $(seq 7); do python3 ../compare.py ./baseline ./optimized; done   # 7 回、中央値を採用

# 診断（性能計測には未使用。ビルドフラグは変えていない）
gcc -O3 -fopenmp -fopt-info-vec-optimized -fopt-info-vec-missed -c optimized.c -o /dev/null
gcc -O3 -fopenmp -Wall -Wextra -c optimized.c -o /dev/null     # 警告なし

# 使い捨ての変体ハーネス（交互測定・n=1..11 の順序検証）で採否を決め、測定後に削除
```

`detect_profilers.py`: 検出言語 c、利用可能ツールは `gprof` のみ（`perf`/`valgrind`/`hyperfine`/`time` は未導入）。
gprof は `-O2 -pg` を要求し、同一最適化フラグで比較する制約と両立しないため使わず、ケース毎の内蔵タイマで比較した。
なお `baseline_vec` / `vec-baseline.txt` は評価時の一時診断ファイルで、リポジトリには含めない。

## 3. 最適化と実測（7 回 × 3 レップの中央値、checksum 全一致）

| case | baseline ms | optimized ms | 速度比 | 手法 |
| --- | --- | --- | --- | --- |
| axpy | 76.905 | 37.009 | **2.08x** | AoS→SoA + init と update の融合（v は update 後どこからも読まれないので実体化しない） |
| matmul | 61.817 | 17.088 | **3.62x** | `i,j,k` → `i,k,j`（内側 j が連続。C は行優先） |
| sum2d | 4.729 | 4.697 | 1.01x（ノイズ） | 列走査 → 行走査 + 4 本の加算鎖 |
| matmul_omp | 18.455 | 8.065 | **2.29x** | 外側 i 並列は維持し、内側を `i,k,j` に変更 |

`matmul_omp` は 7 回で 1.3–4.0x（base 14.0–24.2 ms / opt 4.5–12.9 ms）とばらつきが大きく、中央値 2.3x を採用値とする（`OMP_NUM_THREADS` は未固定 = 12、他プロセスの負荷あり）。他 3 ケースのばらつきは ±10% 以内。

内訳（交互測定した変体。採用版と同一フラグ）:

- axpy: AoS 61.6 / SoA 6 フィールド 3 パス 57.2 / 融合 2 パス 22.3 ms。
  → **SoA 単独はほぼ無効**（同じ 288MB を動くため）。利得の実体は「96MB 構造体配列を 3 パス→2 パスに減らし、死んでいる v の store/load を消した」こと。
  注: 変体は直前のケースが同じヒープを温めていたため 22ms、実バイナリ（axpy が最初の確保）は 37ms。ページフォールト分の差であり、変体の絶対値を baseline と直接比べてはいけない。
- matmul: ijk 61.4 / **ikj 16.7** / ikj+64 行ブロック 17.5 / ikj+32 行ブロック 17.8 ms。ブロッキングは不要（3 行列で 3.5MB、L3 に収まる）ので最小構成の ikj を採用。
- matmul_omp: ijk 並列 15.6 / **ikj 並列 8.6** / ikj+32 行タイル並列 8.9 ms（各 5 回の交互測定の中央値）。タイル化は有意差なし。
  serial/vector/parallel の比較: **並列化だけ（15.6–18.5）より、レイアウト変更だけ（17.1）の方が同等以上**。両方で 8.1。
- sum2d: 列走査 5.01 / 行走査 1 累算 4.83 / 行走査 4 累算 4.17 ms（5 回交互）。ただし実バイナリ比較では 4.73 → 4.70（差はノイズ）。
  72MB の 1 パス走査がシングルコアの DRAM 帯域（約 17GB/s）律速で、**レイアウト変更が効かない唯一のケース**。
- 却下: `sum2d` の OpenMP reduction（`sum_row4_omp`）。1/2/4/6/12 スレッド = 5.60/5.48/4.74/4.43/6.66 ms で、シリアル 4.4–5.1 ms より速くならない（12 スレッドは SMT で悪化）。

## 4. 正しさ

- 全 7 回の `compare.py` で 4 ケースすべて `match = exact`。
  checksum: axpy 3042924015 / matmul 1415565688 / sum2d 45000003 / matmul_omp 1415565688（baseline と一致）。
- matmul / matmul_omp は各要素の k 方向の加算順が baseline と同一なので、整数の結合則に頼らず要素単位でも一致する。
  使い捨てテスト（乱数符号付き値、n=1..11、`mm_ijk` と `mm_ikj` の全要素比較）で PASS。テストは測定後に削除。
- 並べ替えの前提: 行列要素は `(i*7+seed)%11` で最大 10、`n=384`。積和は最大 384×100 ≈ 3.8e4、総和 1.4e9 で int64 の範囲内。`sum2d` も総和 4.5e7 でオーバーフローしない。
  この前提が崩れる（値域が大きく和が 2^63 を超えうる）場合、`sum2d` の 4 累算と走査順変更は厳密一致を保証しない。
- axpy: 融合は 1 要素ずつ `x+vx+3` を先に計算するだけで、加算順も baseline と同一。`v` 配列は update 後に一度も読まれないため削除しても観測結果は変わらない。
- `-Wall -Wextra` で警告なし。

## 5. スキル/スキャナへの指摘

**スキルに欲しかった警告**

1. **大きな malloc の初回タッチ**が、最初に実行されるケースの時間にそのまま乗る。同一バイナリ内の比較なら順位は保たれるが、別バイナリ・別ハーネスで測った同じ関数を比べると 2 倍近くずれる（実測 22ms vs 37ms）。ケース順とウォームアップを固定し、変体は「同一バイナリ内で交互測定」と明記すべき。
2. **整数配列は既定 ISA でベクトル化できないことがある**。`-O3`（`-march` 指定なし）では 64bit 整数乗算の SIMD 命令が無く、行列積の内側ループは `not vectorized: no vectype` になる。ガイドは「まず自動ベクトル化を確認」と言うが、「確認した結果ベクトル化できない場合に、フラグを変えずに何が残るか（レイアウトのみ）」まで書いていない。
3. **シリアルのレイアウト改善が効かないケース**（1 パス大配列 reduction が DRAM 帯域律速）が抜けている。ガイドは「並列化で速くなるとは限らない」とだけ言うが、逆方向（走査順を直しても帯域律速で改善しない、並列化も効かない）の実例がない。
4. **OpenMP 化の制約**: `for (i = 0; i + 4 <= len; i += 4)` のような制御述語は `invalid controlling predicate` でコンパイルできない。`parallel for` に書き換える際は正規形（`q < len/4`）へ直す必要がある、という一言が欲しい。
5. 「変更は一度に一種類ずつ」とあるが、axpy は SoA とループ融合を分けないと**どちらが効いたか誤判定する**（SoA 単独は無効）。ベンチ表に「手法の内訳」欄を設けるべき。

**スキャナの偽陽性/偽陰性**

- 偽陽性: `alloc-in-loop` 3 件（すべてループ外の単発確保）、`modulo`/`division` 5 件（定数除数・セットアップ・1 回だけの処理）。
- 偽陰性: 行列積の非連続内側ループ（53 行）と `sum2d` の列走査（61–62 行）という、この演習の中心的アンチパターンを検出しない。「連続次元を内側で回しているか」の判定が無いため、`openmp-parallel-vector-review` だけでは今回の主目的に届かない。

## 6. 見送った候補

- `restrict` / `__builtin_assume_aligned`: 非エイリアスの根拠が無い。
- `-march=native` 等のフラグ変更: 同一フラグ比較の制約に反する。
- axpy の並列化・modulo のインクリメンタル化: 依頼範囲外かつ未計測のため未実施（axpy の残りコストは初期化ループで、gcc のベクトル化レポートでも未ベクトル化）。
- `sum2d` の並列化: 実測で悪化するため却下（上記）。
