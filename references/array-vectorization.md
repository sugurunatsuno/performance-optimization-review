# 配列/ベクトル化/データ配置/並列化の実装ガイド

このガイドは、ボトルネックが配列演算にある場合のレビュー手順。候補は **必ず実測してから採用** する。スキャナのヒットや SIMD ディレクティブは高速化の証明ではない。

## 共通の判定

- 先にプロファイルする。ループが CPU 計算律速か、メモリ帯域律速か、アロケーション律速かを分ける。I/O 待ちなら配列最適化より原因を優先する。
- 対象の dtype、shape、strides、配置 (C/F order、AoS/SoA)、入力の変更可否、エイリアス、実行環境/CPU 機能を記録する。
- 各反復が独立しているかを確認する。reduction、prefix sum、隣接要素の参照、早期終了、例外、副作用はループ変形を阻む。
- 正確性は契約で判断する。浮動小数点の集約順や FMA、fast-math、整数のオーバーフロー、NaN、符号付きゼロを無条件に変更しない。
- 小/大データ、端数、非正方形、非連続ビューを含めて比較する。SIMD 化やスレッド数の増加が速度を保証するわけではない。

## 並列化

独立した行、チャンク、タイルを外側で分割する。同期、スケジューリング、false sharing、NUMA、ワーカー起動コスト、メモリ帯域の飽和を確認する。

- OpenMP: 最小限の変更なら外側の `#pragma omp parallel for` を比較する。共有バッファへの書き込みが重ならないことを確認する。
- Numba: `prange` は JIT の並列領域としてのみ扱う。依存関係や reduction に注意する。Python の通常の `range` を置換するだけでは並列にならない。
- NumPy/BLAS: 内部でマルチスレッド化されている可能性がある。外部並列と重ねる前にスレッド数を調整し、過剰生成を防ぐ。

小さな要素演算はプロセス/スレッドの起動と通信コストが勝つことがある。

## ベクトル化

### Python と NumPy

型と形状が一致し、各要素を独立して計算する場合はスカラーの Python ループと ufunc/broadcasting を比べる。

```python
# a, b, out は同じ shape の独立した NumPy ndarray とする
for i in range(a.size):
    out[i] = a[i] + b[i]

# 変更候補: 元の out を更新し、余分な結果配列を作らない
np.add(a, b, out=out)
```

- `np.vectorize` は Python 関数を各要素に適用する便宜的なラッパーであり、通常は SIMD 高速化ではない。
- `a * b + c` は中間配列を作りうる。メモリ帯域/割り当てが支配的なら `out=`、適切な融合処理、Numba などを比較する。
- broadcasting でメモリ使用量が増えないか、型昇格、整数/浮動小数点の結果、入力の破壊的変更、エイリアスを確認する。
- 単なる `ndarray` 置換で全ケースが高速化するとは限らない。配列の生成と変換を含めた時間を測定する。

### C / C++ の SIMD

まずコンパイラの自動ベクトル化を調べる。GCC なら `-O3 -fopt-info-vec-optimized -fopt-info-vec-missed`、Clang なら `-O3 -Rpass=loop-vectorize -Rpass-missed=loop-vectorize` を既存のビルドに合わせて診断用に使用できる。診断フラグによる確認と実運用の性能計測は分ける。

- 連続アクセス、反復間依存なし、ループ内の複雑な分岐なし、適切な型を優先する。
- ポインタが重ならないという根拠なしに `restrict` を付けない。アラインメントを保証できないなら仮定しない。
- SIMD 専用命令や高い ISA を要求する変更は、対象 CPU と非対応環境へのフォールバックを確認する。
- 指示を追加するより先に、コンパイラが既に SIMD 化していないか確認する。

## データ配置の最適化

| 対象 | 検討する案 | 確認すること |
| --- | --- | --- |
| C order の 2D 配列 | 連続する最後の次元を内側で走査 | strides、依存、reduction 順序 |
| F order の 2D 配列 | 連続する最初の次元を内側で走査 | 実配列の順序、転置ビュー |
| 大きな行列/ステンシル | タイル化してキャッシュ再利用 | タイル端、halo、依存、タイルの費用 |
| AoS (`items[i].x`) | x など頻出フィールドを SoA に分離 | API/ABI、追加コピー、全フィールド走査 |
| ストライド付きビュー | 必要に応じて連続バッファを一度だけ作る | 変換/書き戻し費用、メモリ上限、所有権 |

たとえば C order の `a[:, j]` は列方向の非連続アクセスになりやすいが、転置や `ascontiguousarray` で必ず速くなるわけではない。後続の再利用回数と変換費用で採否を決める。

並列ループでタイルを分割するときは、同じキャッシュラインの別要素を書き込む false sharing と、CPU 間のデータ移動を確認する。

## 並列化 + ベクトル化

外側で独立した仕事を分割し、内側で連続した要素を計算する方法を優先して検討する。次は `a`、`b`、`out` が別領域で、行ごとの書き込みが重ならない場合の例。

```c
// 既存ビルドで OpenMP が有効な場合。cols は正、積 rows*cols は有効範囲内とする。
#pragma omp parallel for schedule(static)
for (int r = 0; r < rows; ++r) {
    #pragma omp simd
    for (int c = 0; c < cols; ++c) {
        size_t i = (size_t)r * (size_t)cols + (size_t)c;
        out[i] = a[i] + b[i];
    }
}
```

ここで SIMD は内側の演算が独立であることを前提にする。依存、別名参照、例外、計算順の制約がある場合は指示を付けない。環境によっては `parallel for simd` の一重ループも選択肢だが、メモリ配置と仕事量で比較する。

NumPy の大きな一括演算を Python の並列タスクで細かく分割すると、分割/転送/BLAS の内部スレッド数によって逆効果になる場合がある。Numba の外側 `prange` + 内側の連続ループを使う場合も、JIT の SIMD 診断を確認する。

## 比較方法と採用条件

同じ入力/型/計測条件で以下を比較する。

| ケース | 計測対象 |
| --- | --- |
| serial | 最適化前の単一スレッド |
| parallel-only | 外側の並列化だけ |
| vector-only | ベクトル化またはデータ配置の改善だけ |
| combined | 並列化とベクトル化を併用 |

レイアウト変更を行うなら変換コストを含む総時間と、変換済みデータを再利用する計算部分の時間を分けて記録する。スレッド数、SIMD の実際の適用、メモリ使用量、CPU/コンパイラ/最適化フラグ、中央値と測定回数を残す。

正しさと既存 API を維持し、代表入力で再現可能な改善があった変更だけを採用する。詳細は `references/verification.md` に従う。
