# 最適化候補の判定基準

このファイルは候補の辞書。すべてを機械的に適用せず、計測結果と意味論で選ぶ。

## アルゴリズムとデータ構造

| 候補 | 検査観点 | 条件と注意 |
| --- | --- | --- |
| 計算量の改善 | 二重走査、毎回の全検索、重複ソート | O(n²) → O(n log n) などを優先。ただし追加メモリを考慮 |
| 再計算の排除 | 同じ入力の関数/検索/フィルタを繰り返す | 入力や外部状態が変わらないこと。キャッシュ無効化を検討 |
| 前計算とメモ化 | ルックアップや固定係数の計算が多い | 前計算コスト、メモリ、データ鮮度に注意 |
| バッチ化 | 細かい DB/ネットワーク/ファイル操作が多い | エラー/トランザクション/順序/遅延の制約に注意 |

## 演算回数とループ

| 候補 | 典型例 | 機械的に適用しない理由 |
| --- | --- | --- |
| ループ不変式の移動 | 毎回変わらない係数/配列長/参照をループ外で計算 | 副作用/エイリアシング/例外発生位置/変化するグローバル |
| 共通部分式の除去 | 同じ純粋な計算を複数回する | コンパイラが既に除去する場合あり。変数の更新や副作用に注意 |
| 乗算の削減 | 変わらない積を前計算、Horner 法の利用 | 浮動小数点では演算順と誤差が変わる。単純な `x*2` → `x+x` は原則不要 |
| 除算の削減 | 不変の除数での繰り返し除算を検出 | 浮動小数点の逆数乗算は数値的に同値とは限らない。整数には使わない |
| 添字計算の削減 | 深い多次元インデックスを一次元参照に変える | 境界チェック/レイアウト/エイリアシング/サイズの積のオーバーフロー |
| 関数呼び出し削減 | 極短関数が極めて高頻度に呼ばれる | インライン化済みか確認。コード肥大や命令キャッシュを考慮 |
| ループ展開 | 小さな固定回数の内側ループ | コンパイラの自動展開、命令キャッシュ、レジスタ圧力を考慮 |

## 配列とメモリアクセス

- C/C++ の通常の `T a[R][C]`、C-order の NumPy 配列、一般的な一次元バッファの row-major 実装では、`for row` の内側で `for col` を回す方が連続アクセスになりやすい。
- Fortran、Julia、MATLAB、Fortran-order の NumPy 配列では、一般に列優先。`for col` の内側で `for row` を回す方が連続アクセスになりやすい。
- Python のリストのリストは NumPy の密な 2 次元配列と同一の連続レイアウトではない。Python ループはインタプリタのコストが支配的になりうる。
- 転置ビュー、スライス、負のストライド、SoA/AoS、パディング、GPU、SIMD の都合で単純な「行→列」則が成立しないことがある。
- 読み出し順だけでなく書き込み競合、データ依存、reduction の順序、早期 `break` / `continue`、I/O、例外の順序も確認する。
- 行列積では走査順変更に加えてブロッキング/タイル化や最適化済み BLAS の利用が効くことが多い。ただしライブラリ依存、データ変換費用、契約を確認する。
- 毎回の配列コピー、不要な一時配列、ループ内の確保、不要な boxing を調べる。共有状態や所有権/寿命の条件を崩さない。

## 分岐、並列化、SIMD

配列処理は `references/array-vectorization.md` の実装例と採用条件を参照する。検討順は「既存の並列処理が有効か → 独立した要素演算をベクトル化できるか → メモリ配置/アクセスを改善できるか → 並列化と SIMD を組み合わせるか」。これは固定の適用順ではなく、測定したボトルネックと依存関係で前後する。

| 候補 | 有効になりやすい条件 | 見送る条件 |
| --- | --- | --- |
| NumPy の配列演算/ufunc | 配列全体で独立した同種演算を反復 | Python list、異なる dtype、巨大な一時配列、任意の副作用 |
| C/C++ 自動 SIMD | 連続アクセス、独立した反復、明確な別領域 | 依存、混在型、未知の alias、既に SIMD 化済み |
| 行列のタイル化/レイアウト変更 | 大規模な非連続アクセス、再利用可能な変換後配置 | 変換の方が重い、ビュー/ABI 契約が変わる |
| SoA / AoS の選択 | 一部フィールドだけの大量連続処理 | 構造体を一体で扱う頻度が高い、互換性を壊す |
| 外側並列 + 内側 SIMD | 独立したタイル/行が多く、内側に連続演算がある | 小入力、メモリ帯域飽和、false sharing、reduction の順序制約 |


- 分岐予測ミスがホットスポットにあり、分岐なしの式が検証可能なら比較する。分岐を消すことで必ず速くなるわけではない。
- SIMD 化はデータ型、アラインメント、境界処理、コンパイラフラグ、ベクトル化レポートを確認する。
- 並列化はスレッド数を増やす前に競合、同期コスト、偽共有、メモリ帯域を調べる。
- ループ順序の変更で parallel reduction の結果が非決定的になる場合は契約違反を疑う。

## 数値計算の安全性

### 除算を逆数乗算にする場合

次は浮動小数点で一般に厳密同値ではない。

```text
x / d
x * (1.0 / d)
```

- 逆数 `1/d` 自体がオーバーフロー/アンダーフローする可能性がある。
- 丸めが 1 回から 2 回に増えたり、丸め位置が変わることがある。
- 除数 `d` が 0、非有限値、極端に大きい/小さい値の場合を含めて検証する。
- 浮動小数点例外、`NaN`、無限大、符号付きゼロ、flush-to-zero、コンパイラの fast-math 設定を確認する。
- `d` が各反復で変わる場合は逆数を外に出さない。
- 厳密一致が必要ならこの変形を採用しない。許容誤差契約があるときのみ測定する。

### その他の代数変形

- `a * (b + c)` と `a*b + a*c`、`(a+b)+c` と `a+(b+c)` は浮動小数点では一般に等価でない。
- `pow(x,2)` → `x*x` も、型、例外/オーバーロード、整数指数の意味、特殊値を確認する。
- 整数の `x/2` → `x>>1` は負値、丸め、符号付き型、言語仕様を要確認。定数除算はコンパイラが最適化することが多い。
- 符号付き整数のオーバーフロー、符号なし整数のラップ、型の昇格/縮小は言語ごとに異なる。

## 言語ごとの注意

- C/C++: 最適化フラグと対象 CPU、未定義動作、`restrict`/エイリアシング、ベクトル化レポート、未初期化領域。
- Rust: イテレータの最適化、境界チェック、所有権、リリースビルド、checked/wrapping/saturating 演算。
- Python: 純 Python ループのオーバーヘッド、NumPy の一時配列、型変換、プロファイラ、Numba/Cython 等の追加依存。
- Java/JavaScript/.NET: JIT ウォームアップ、GC、インライン化、型の安定性、ベンチマークフレームワーク。
- GPU: データ転送、coalesced access、同期、occupancy、実行非同期性。

## 優先順位の目安

高優先: 実測の支配的箇所、計算量の改善、無駄なコピーや確保、明らかな重複仕事。

条件付き: ループ入れ替え、タイル化、共通部分式、関数の融合、ベクトル化。

低優先または原則見送り: 根拠のない演算子置換、コンパイラが既に実施する単純な強度削減、読みにくくなる微小変更、許容誤差のない浮動小数点再結合。
